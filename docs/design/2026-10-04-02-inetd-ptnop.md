# Design: `sonda-inetd-ptnop`

## Purpose

Run ptnop measurements inside a long-lived process reached over a
Unix socket, instead of spawning `sonda spool run` and
`sonda measure-ptnop` for each measurement.

## Why a server

- `sonda scan` used a lot of CPU, and we traced it back to spawning
several short-lived processes per measurement. Creating a process
costs more than sending a message, and the plugin design causes
more executions than strictly needed.

- With the server, a typical scan went from 3-5 seconds of CPU to
less than one second (see `2026-06-25-00-measure.md`).

- The server merges the logic of `sonda measure-ptnop` and
`sonda spool run` into a single linear flow. So the spool is now
more a directory protocol than a command: `spool run` remains for
commands that run rarely and do not need the optimization.

## systemd socket activation

- `sonda-inetd-ptnop.socket` listens at `/run/sonda/inetd-ptnop/sock`
with `Accept=yes`: systemd starts one `sonda-inetd-ptnop@.service`
per connection, with the connection on stdin and stdout and stderr
going to the journal.

- `sonda scan` uses a single connection for all its steps, so a scan
costs one server process.

- The service runs as `_sonda:_sonda`, can only write
`/var/spool/sonda`, and is otherwise restricted like the other
units (see `2026-06-26-00-debian-packaging.md`).

- `--stdio` disables the assumption that stdin is a socket, for
manual testing. The `--help` output shows how to test with
`systemd-socket-activate` and `nc -U`.

## Wire format

- `internal/ptnoprpc` defines it: one JSON request per line, one JSON
response per line, in order, until the client closes the connection.

- The client may set an opaque `id`, which the server echoes back.

- On success, the response carries `spanId`, `spanDir`, and an
`exitCode` of `0` (success) or `1` (measurement failure).

- On failure, the response carries `error`. Errors starting with a
usage error prefix tell the client that its input was wrong (e.g., an
invalid pipeline name) rather than that the server failed. The
exit code cannot carry this, since it only exists once the span
directory has been created.

- A request line is limited to 512 KiB, which is generous for small
JSON objects, even with many HTTP headers or tags.

## Who may connect

- The socket is `0660 _sonda:_sonda`, so any member of the `_sonda`
group can start measurements. What the server does is no more
dangerous than what `curl` and `dig` already allow.

- So the spool and metrics directories also belong to the `_sonda`
group: users who can start measurements can read the results,
without also joining the broader `adm` group.

- The server records the peer credentials (UID, GID, PID) in each
span's `peer.json`, for accounting. The kernel provides them, so
they can be trusted. UID and GID are the useful part: the process
may be gone by the time someone reads the spool. This only works
on Linux, and the fields are `-1` when unavailable.

## Bounding resources

- `MaxConnections=8` instead of the default 64, which is too
permissive for collecting ptnop logs.

- With a connection limit, idle clients could starve new ones. So
the server closes a connection after `--idle-timeout` (default
`60s`, `inetd.ptnop.idle-timeout` in `config.toml`) without I/O.
The timeout only applies while waiting for the client to send a
request or read a response, not while a measurement runs. It is
ignored with `--stdio`.

- All units run in `system-sonda.slice`, so systemd accounts for
the resources sonda uses as a whole.

## `sonda measure-ptnop` as a client

- `sonda measure-ptnop` is now a thin client of the server: it needs
access to the socket and fails when the server is not running.

- It refuses to run under `sonda spool run`: the server mints the
span ID, so the results would be duplicated under a second span
with the wrong ID.

- `--dry-run` prints the request instead of sending it, so it can be
piped into `sonda-inetd-ptnop --stdio` or `nc -U` for testing.

- See `2026-06-25-00-measure.md`.
