# Design: `sonda spool gc`

## Purpose

Removes stale span directories from the spool. Without periodic
cleanup the spool grows without bound, since `sonda spool run`
and `sonda-inetd-ptnop` create a new span directory for every
measurement.

## How it works

The command treats each subdirectory of the spool root as a data
type directory (e.g., `ptnop`). For each data type, it walks the
sharding tree (`<dataType>/XXXX/X/X/<spanID>`) and removes every
span directory whose UUIDv7 timestamp is older than a configurable
cutoff (default: 6 hours). Both final and `.tmp` (crash-orphaned)
directories are eligible for removal.

After removing spans, the walk prunes empty sharding directories
on the way back up, so the tree stays compact. Data type directories
are never removed, even when empty: they are part of the spool
structure rather than sharding artifacts.

A single invocation covers every data type, including future ones,
with the same `--max-age`. Per-data-type retention is not needed yet.

## Flags

- `--spool-dir DIR` — root of the spool tree, containing the data
  type directories (default: `/var/spool/sonda`).
- `--max-age DURATION` — remove spans older than this (default:
  `spool.gc.max-age` in `/etc/sonda/config.toml`, otherwise `6h`).

## Scheduling

The Debian package runs `sonda spool gc` from its own systemd
timer (`sonda-spool-gc.timer`): one minute after the timer
starts, then one hour after each run finishes.

The service passes no flags, so the settings come from
`/etc/sonda/config.toml`: a flag would override the config file.

A dedicated timer keeps the spool bounded regardless of whether
scans run, and keeps maintenance separate from measurements.

`sonda-etl-ptnop-prom` drains its work units every 30 s, so
`--max-age` does not affect it.

## Disk Usage (ptnop)

Every `ptnop` measurement adds data to the spool. We measure
the spool usage in 4 KiB block terms. Accounting for `stdout.txt.gz`,
`body.bin.gz`, and the span dir (but excluding sharding dir and
the file system journal), here is what measuring consumes:

- with `optimize=size` and `httpBodyFile=false`, a minimum of
  two blocks (one for the span dir, the other for `stdout.txt.gz`)
  and a realistic outcome of 2-3 blocks per span (mean ~2.3;
  observed max 3 blocks).

- without `optimize=size`, the span size grows linearly with
  the network I/O events but the gzip compression of `stdout.txt`
  amortizes this effect; each network I/O operation emits a
  start+done event pair, about 520 bytes of uncompressed JSON.

- with `httpBodyFile=true`, we recommend `maxHttpResponseBodySize`
  to cap the maximum body size and keep the block count bounded,
  again keeping in mind that compression should amortize the cost.

- a scan of the global citizen-lab/test-lists list with
  `maxHttpResponseBodySize=131072` and gzip compression generated
  spans where the p50 number of blocks per span is 2, the p90
  is 4, the p99 is 12, the observed max is 37, and the mean is 2.68.

## Why a separate subcommand

- Keeps `spool run` and `scan` free of cleanup logic.
- Users and operators can run GC independently (different
  retention, ad-hoc cleanup, dry-run wrapper) without touching
  the measurement path.
- Testable in isolation: no dependency on the measurement stack.

## Safety properties

- Only directories whose name (minus `.tmp` suffix) parses as a
  valid UUIDv7 are considered. Other entries are silently skipped.
- `os.Remove` on sharding directories only succeeds when they
  are empty, so a concurrent `spool run` writing into the same
  shard cannot lose data.
- A span that is still being written lives under a `.tmp` name
  and will only be removed if its UUIDv7 timestamp is older than
  the cutoff — normally impossible unless the writing process has
  been stuck for longer than `--max-age`.

## What this is not

- Not a background daemon. GC runs once and exits, and the
  systemd timer runs it periodically.
- Not a data-retention policy. The default 6-hour window is
  sized for the current "collect and inspect" workflow. A real
  retention policy will live in whatever ingestion pipeline
  eventually consumes the spool.
