# Design: plugins and subcommand re-execution

## Purpose

Allow `sonda` to grow by adding external executables as subcommands,
without changing the single-binary layout or the built-in commands.

It may also allow splitting off existing subcommands that are not
core to `sonda`.

## Re-execution engine

- Implemented at `./internal/reexec`

- `testable.Environ.ReExec` runs a sonda subcommand as a child
process of the current executable. `Environ.AsExitCode` maps the
resulting error to the corresponding exit code.

- On context cancellation, the child receives `SIGINT` first and
`SIGKILL` after a five-second grace period.

- Every place that used to exec `sonda` directly now goes through
`ReExec`; e.g., `spool run`.

- Breaking change: `spool run` used to execute an arbitrary command
and now only executes sonda subcommands. The inner argv no longer
carries the executable path. The rationale is uniform execution of
subcommands, and the freedom to switch between in-process and
external-binary execution as needed.

- Subcommands read their `Environ` from the context rather than
from `testable.Env` (global var), so a subcommand can invoke another
one with a modified environment. This keeps open the option of
running a subcommand in process rather than as a child.

## Plugins

- Implemented at `./internal/plugins`

- A plugin is an executable named `sonda-<name>`, with `<name>`
matching `^[a-z][a-z-]*$`, located in `$SONDA_EXEC_PATH`. It must be a
regular file, executable by user, group, and other, and neither
setuid nor setgid. If `SONDA_EXEC_PATH` is empty, no plugin is
loaded, and the plugin feature is disabled.

- `sonda <name> args` executes `$SONDA_EXEC_PATH/sonda-<name> args`
through the re-execution engine, so exit code, stdio, and signal
handling are the same as for built-in subcommands.

- Plugins are registered after built-in commands. A plugin whose
name matches a built-in command is skipped with a warning on stderr.

- If `$SONDA_SHARE_PATH/plugins/sonda-<name>.txt` exists, its first
line is the plugin's short description in `sonda --help`. Without
it, the plugin works but is not listed.

- `SONDA_COMMAND` is set by `sonda` to its own absolute path, so that a
plugin can reinvoke the exact `sonda` executable that invoked it.

- `SONDA_TRACE_PLUGIN=1` traces plugin discovery on stderr.

## Design iterations

- 2026-09-22: explored splitting sonda into separate binaries
under a libexec directory, with `sonda` as a launcher only. What
initially landed kept the single binary while allowing plugins
next to it.

- Computing the plugin directory from `os.Executable()` was
rejected: the directory comes only from `SONDA_EXEC_PATH`.
