# Design: triggers

## Purpose

Let `sonda scan` start the ETL pipelines as soon as it has created
new spans, instead of having each pipeline poll the spool from a
timer.

## Producer

- `default.yml` lists the triggers to fire (today, `etl-ptnop-prom`).
Names not in `triggers.ValidName` are logged and skipped.

- At the end of a scan that created spans, `sonda scan` writes a work
unit at `/run/sonda/scan/<UUIDv7>.jsonl`, one `triggers.CreatedSpan`
(`dataType`, `spanDir`, `spanId`) per line.

- It then hard-links the work unit into `/run/sonda/<trigger>/` for
each trigger and removes the original. A consumer thus sees a
complete file, and each consumer removes its own link.

## Consumer

- A `.path` unit with `DirectoryNotEmpty=/run/sonda/<trigger>` starts
the service with the same name. It is enabled through
`WantedBy=paths.target`. If the directory is already non-empty when
the path unit starts, the service starts immediately.

- Invariant: when a run ends, the consumer has removed every work
unit it saw, including invalid or failed ones. Otherwise the path
unit fires again and again until it hits the start limits
(`StartLimitBurst=`, see `systemd.unit(5)`).

- Dotfiles in the directory do not trigger the path unit.

## Directories

- `/run/sonda/scan` and `/run/sonda/<trigger>` come from
`tmpfiles.d/sonda.conf`, owned by `_sonda`, mode `2770`, with a 1h
age. Linking requires the same file system, which `/run` guarantees.

- Adding a trigger means touching `default.yml`, `ValidName`,
tmpfiles, and adding the `.path` and `.service` units.

## What we give up

- `/run` is a tmpfs: a reboot, a failed run, or the 1h tmpfiles
cleanup drops pending work units. The spans stay in the spool until
`sonda spool gc` removes them, but no pipeline processes them. We
accept this loss for now.
