# Design: data types

## Purpose

Explain how sonda separates the data it stores by type, both in
the spool and in the metrics directory, and why each command
knows its own data type.

## Layout

- Raw results: `/var/spool/sonda/<data-type>/XXXX/X/X/<spanID>/`.
See `2026-06-25-01-spool-run.md` for the sharding.

- Processed metrics: `/var/lib/sonda/metrics/<data-type>/...`. For
`qoe`, the daily files are `qoe/YYYY/MM/DD/YYYY-MM-DD.parquet`.
See `2026-06-26-05-metrics-load.md`.

- A data type directory always tells what kind of data is inside,
so the output of one engine never mixes with another's.

## Who uses which data type

| Command | Reads | Writes |
|---|---|---|
| `sonda-inetd-ptnop` | | `<spool-dir>/ptnop` |
| `sonda spool run` | | `<spool-dir>/<data-type>` (default `_`) |
| `sonda spool gc` | every `<spool-dir>/*` | removes old spans |
| `sonda etl-ptnop-qoe extract` | `<spool-dir>/ptnop` | `qoe.parquet` in each span |
| `sonda etl-ptnop-qoe load` | `<spool-dir>/ptnop` | `<metrics-dir>/qoe` |

## Naming

- A measurement engine's data type is the engine name (`ptnop`).

- An ETL plugin is named `etl-<source>-<dest>`: it reads the
`<source>` spool data type and writes the `<dest>` metrics data
type.

- Files that an ETL plugin adds to a span are named after `<dest>`
(`qoe.parquet`, `qoe.loaded`), so several ETL plugins can process
the same span.

- `spool run --data-type` must match `^[_a-z][_a-z0-9-]*$`, which
also guarantees a single path component. The default, `_`, names
data whose type is unspecified but that still needs a directory.

## Flags take the top-level directory

- `--spool-dir` and `--metrics-dir` are the top-level directories,
and each command appends its own data type.

- So a single `sonda spool gc` covers every data type, including
future ones, without one invocation per data type.

- And a caller cannot pair a command with the wrong data type
directory, since the command, not the caller, picks it.

- The top-level directories default to `/var/spool/sonda` and
`/var/lib/sonda/metrics`. They are constants rather than
`config.toml` settings, because `postinst`, `postrm`, and the units'
`ReadWritePaths=` also depend on them. To relocate them, use a bind
mount or a symlink.

## What gc does with data type directories

- gc treats every subdirectory of the spool as a data type and walks
its sharding tree.

- It never removes a data type directory, even when empty: data type
directories are part of the layout, not sharding artifacts.

- gc does not remove spans that live outside a data type directory
(e.g., directly below `/var/spool/sonda`, which is where they lived
before data types existed). Those need manual cleanup.
