# Design: `sonda measure-ptnop`

## Starting principle

Gall's Law: a complex system that works evolved from a simple system
that worked. We started with the simplest useful measurement primitive
and grew from there. Then we added a remote process (`sonda-inetd-ptnop`)
when measurement showed that CPU usage was excessive. A typical run with
default configuration used 3-5 seconds of CPU. When using the remote
process and the Unix socket, this number became less than a second.

While the `sonda measure-ptnop` command has since evolved to just
become a frontend for `sonda-inetd-ptnop`, the current design still
reflects the original simplicity of executing a command and
getting its result. The main difference, now, is that the measurement
runs inside the `sonda-inetd-ptnop` process rather than inside
`sonda measure-ptnop` itself.

## Shape of a measurement command

- The invocation runs in a remote process (`sonda-inetd-ptnop`) and the
communication uses a Unix socket and a simple RPC protocol, still
simulating the direct execution of a measurement process.

- Each `sonda measure-ptnop --pipeline=foobar ...` pipeline is a standalone
invocation with flags controlling its behavior. No positional arguments.

- Flat structure: the typical consumer is a script or another `sonda`
subcommand, so avoid a complex subcommand hierarchy.

- Each primitive should fail in exactly one way. For example,
`sonda measure-ptnop --pipeline=dns-over-https` takes IP:port, SNI, HTTP host,
and URL path as separate flags rather than a domain name that
would need resolving first. The caller composes the resolution
and the DoH query as separate steps.

- Flags use `vflag` with `@DEFAULT_VALUE@` interpolation such that
`--help` always shows current defaults. Flag names are lowercase
kebab-case (e.g., `--dns-query-type`, `--http-host`, `--url-path`).

## Output contract

- Primary output: NDJSON on stdout. The first line is a
`sondaRemoteMeasurementResult` event containing the remote results
communicated by the `sonda-inetd-ptnop` process, including the span
ID and the span directory (i.e. the directory within the spool containing
the results of the specific measurement). The following lines are
a copy of the span's `stdout.txt`.

- Before `sonda-inetd-ptnop`, `sonda measure-ptnop` wrote the structured
logs on stdout while measuring. We preserve this behavior by copying
`stdout.txt` to stdout, with one difference: the copy happens after the
measurement completes, so the logs are not streamed in real time.

- Side effect: structured NDJSON logs on `stdout.txt` in the span
directory, one JSON object per line; `request.json` in the same directory
contains the RPC request sent to the remote server.

- Exit code: signals success (0), measurement failure (1), usage
error (2), failure to dial the `sonda-inetd-ptnop` socket (3), or
any other error (4).

- All log entries in a measurement share a `spanId` (UUIDv7),
minted by `sonda-inetd-ptnop`, for correlation.

- Log messages are single camelCase words (e.g., `tlsHandshakeStart`,
`sondaFailure`, `connectDone`) to simplify downstream filtering.
See `2026-06-26-01-structured-log-discipline.md` for the full
naming rules and event inventory.

- All measurement commands accept a repeatable `--tag KEY=VALUE`
flag. Tags are injected into every structured log line via
`logger.With`, so they appear on all events emitted by that
measurement. This is the mechanism for propagating session-level
context (e.g., reflexive addresses) into individual spans without
changing the ptnop pipeline or the measurement interfaces.

- Optional: the HTTP response body can be saved as `body.bin`
inside the span directory for debugging (`--http-body-file`).

## Processing is out of scope

- The consumer of structured logs and exit codes is a separate
component. `sonda measure-ptnop` does not aggregate, retry, loop,
or decide what to do with results. It measures once and exits.

- Because `sonda-inetd-ptnop` already creates a span for each
measurement, `sonda measure-ptnop` refuses to run inside
`sonda spool run` (detected through `SONDA_SPAN_ID`), which would
otherwise create a span inside a span.

## Why CLI-shaped primitives

- The current system does not shell out to these commands: `sonda scan`
already talks to `sonda-inetd-ptnop` directly using `ptnoprpc`.
But designing each measurement as a self-contained CLI allows
fast experimentation and evolution without coupling.

- `sonda measure-ptnop --dry-run ...` prints the RPC request
instead of sending it. Piping it into `sonda-inetd-ptnop --stdio`
runs a measurement without the socket-activated service, which
is useful for testing.

- Bonus: users can invoke measurements in ways we did not
anticipate, compose them with shell pipelines, or integrate
them into their own tooling.

## What we know about the goal

- The goal is to measure quality of experience (QoE) across
multiple layers: DNS, TLS, HTTP, streaming, throughput.

- Each primitive measurement layer becomes a `sonda measure-ptnop --pipeline=foo`
pipeline following the same pattern established here.
